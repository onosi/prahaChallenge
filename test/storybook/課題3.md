# 課題3-1

## メリット
1. コンポーネント単位での独立開発ができる
    - アプリ全体を立ち上げずにUIコンポーネント単体を表示・確認できるため、開発効率が上がる。
2. デザインと実装の単一ソース化（Design ⇄ Code の同期）
    - コンポーネント単位で「見た目＋挙動」をドキュメント化できるため、デザイナーが意図したバリエーション（色・サイズ・状態）をコードで正確に確認・承認できる。
    - ボタンやフォームなどをStoryで一覧化すると再利用性が高まり、同じコンポーネントをチーム全体で使うことでビジュアルの一貫性が保てる。
3. 状態やバリエーションを簡単に再現できる
    - 例えばエラー状態、ロード中、データ有り/無しなど、アプリの状態を模擬して見た目や挙動を確認できる。

## デメリット
1. 設定や環境構築の工数がかかる
    - 最初の導入コストが高い(viteだととくに大変だった)
2. 本番環境との動作差が出る可能性
    - Storybook内のモックデータやスタイルが、本番アプリと完全に一致しない場合がある
    - アプリ固有のコンテキスト（グローバルCSSやテーマ切替、データフェッチ）と差異が出るとデザイナーが見たものと本番がずれる
3. メンテナンスコストがかかる
    - コンポーネントを変更した際にStoryやMockも更新しないと、ドキュメントが古くなる。
    - デザイン側の変更（Figmaなど）をStoryやトークンに反映する運用が必要。放置するとStoryが「ドキュメント負債」になりやすい。
    - デザイナーがStory上で「これが正」として細かな見た目を指定しすぎると、実装側が調整する余地がなくなり速度が落ちる／小さな差異で衝突が起きる。
