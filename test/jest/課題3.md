# 課題3-1

- 例外処理に関するロジックが含まれているため、DIを行わないと例外系のテストが難しい
- DB疎通部分については、意図的に例外が起こせないので、例外時の挙動はモックをはさむ必要がある
- API疎通部分については、レスポンスにランダム性があるため、モックを行わないとテストをするのが難しかった

# 課題3-2

- 依存性の注入とは、メソッド内で利用するインスタンスを、メソッドの外部から受け渡す実装のこと
    - メソッド内でインスタンス生成している状態ではない
- 単体テストを実装するときにmockがはさみやすいというメリットがある
    - メソッドとクラスの結合度の高さを解消することで、再利用がしやすいロジックとなる
    - また外部サービスへのリクエストを行う際に別サービスにリクエストをとばしやすいというメリットもある

# 課題3-3

- テストの実行速度が遅くなる
- 外部APIを利用することで、安定性・再現性が下がる
- ただ、外部依存∧プライベート依存である場合には、テスト時に疎通することもそこまで問題がないはず
    - APIが自前で作成しているものである場合には、疎通することもOK
    - またDBサーバーなどの場合には、疎通することによりリグレッションが発生する可能性が低くなる

# 課題3-4

- 単体テスト
    - 一つの関数やクラスの内部ロジックの機能を担保するテスト
    - 外部依存については、プライベート依存は本物を使い、それ以外はモックを使う
- 統合テスト
    - API単位での動作確認テスト
    - 外部依存については、可能な限り全て本物を使う

# 課題3-5

- 課題2を実施する際に、例外が発生しない形式に書き換えてしまっていたので発生せず
- 論理的に空配列を引数に呼び出されることはあり得るが、例外を返すこと自体が開発者の直観に反する
- 例外を返却する場合でも、戻り値として例外であることを明示したほうが可読性が高いコードとなる
    - 例外扱いする場合でも、Either型の概念を導入したほうがよい

# 課題3-7

- Property Based Testingとは、ランダムな入力データを生成してテストを実行し、アプリケーションがさまざまなシナリオで正しく動作することを検証すること
    - Example Based Testingは特定の入出力に対するテストのこと
- 人間が洗い出しづらい境界値やレアケースについてテストが行われる可能性がある
- ただテストの実施時間が長くなるため、外部依存への通信が行われる処理や仕様が明快なテストケースについては、採用しないほうがよさそう

# 課題3-8

- 可読性
    - Gherkin記法でテストケースを記載する
    - 単体テストコード = 品質保証に使える仕様書であることを意識し、メソッドの仕様を明らかにするような名前を書く
- 保守性
    - ブラックボックスの観点でテストケースを記載する
    - ソースコード変更でテスト結果が変わらず、メソッドの仕様でテストケースが変わることを意識する
- 実行速度
    - テスト間の依存を排除し、実行時には並列実行するようにする
