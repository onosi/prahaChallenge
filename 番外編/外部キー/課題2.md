# 課題2-1

MySQLで設定可能な参照アクション
それぞれの参照アクションを設定するべきケース

## MySQLの参照アクション
MySQLでは、外部キー制約に関連する参照アクションを以下のように設定できます:

1. **CASCADE**: 親テーブルの行が削除または更新された場合、子テーブルの対応する行も削除または更新されます。
   - 使用例: 親子関係が強く結びついている場合。

2. **SET NULL**: 親テーブルの行が削除または更新された場合、子テーブルの外部キー列がNULLに設定されます。
   - 使用例: 子テーブルのデータが親テーブルの削除後も保持されるべき場合。

3. **SET DEFAULT**: 親テーブルの行が削除または更新された場合、子テーブルの外部キー列がデフォルト値に設定されます。
   - 使用例: デフォルト値を使用してデータ整合性を保つ場合。

4. **NO ACTION**: 親テーブルの行が削除または更新されても、子テーブルには何も影響を与えません。
   - 使用例: 外部キー制約を無視する場合。

5. **RESTRICT**: 親テーブルの行が削除または更新されるのを防ぎます。
   - 使用例: 親テーブルのデータが重要で削除や更新を防ぎたい場合。

## ケースごとの設定例と理由

### CASCADE
- **例**: 注文（orders）と注文詳細（order_items）の関係
- **理由**: 注文が削除された場合、その注文に紐づく注文詳細は意味がなくなるため、自動的に削除されるべき。注文詳細は注文なしには存在し得ないため、親子関係が強く結びついている。

### SET NULL
- **例**: ユーザー（users）とブログ投稿（posts）の関係
- **理由**: ユーザーアカウントが削除されても、そのユーザーが作成したブログ投稿は残しておきたい場合がある。投稿者を「匿名」として扱うことで、コンテンツの価値を保持できる。

### SET DEFAULT
- **例**: 商品（products）とカテゴリ（categories）の関係
- **理由**: 特定のカテゴリが削除された場合、商品を「未分類」などのデフォルトカテゴリに移動させることで、商品データを保持しつつ、カテゴリの整合性を保つことができる。

### NO ACTION
- **例**: 一時的な参照関係や、アプリケーション側で制御したい場合
- **理由**: データベースレベルでの制約チェックを延期し、アプリケーションロジックで複雑な業務ルールを適用したい場合に使用する。ただし、データ整合性のリスクがあるため慎重に使用する必要がある。

### RESTRICT
- **例**: 部署（departments）と従業員（employees）の関係
- **理由**: 部署に所属している従業員がいる限り、その部署を削除することは業務上適切ではない。まず従業員を他の部署に移動させてから部署を削除するべきであり、誤操作を防ぐためにRESTRICTを使用する。

# 課題2-2

## 想定されるリスク
- 部署データを削除する場合、紐づく全ての従業員データが削除される可能性がある
    - 例: 組織再編に伴い部署データを削除するなど
    - ただ、従業員が1つの部署のみに紐づくとは限らないので、1対多のテーブル構成自体が疑問。
        - 所属関係を示すときには、中間テーブルを作成し多対多の関係にするべき。
        - そのうえで一つ以上の部署に紐づいているという整合性は、アプリケーション層で保持するべき
- 部署データに伴い削除された従業員のデータをログに残すことが難しくなる
    - 特別にログを出力する処理が必要になる
- 例えば、部署テーブル自体に対して外部キーを張っているテーブルがありそのテーブルもon delete cascadeを指定している場合、データが連鎖的に削除されてしまう

# 課題2-3

## 想定されるリスク
- 担当者データが削除された場合、担当者がアサインされていないissueが発生する
    - アプリケーション層であれば早期リターン節を作って事前チェックする可能性があるが、SQLで担当者の棚卸等を行う場合には整合性を担保できない
- 勝手に値がnullに変わってしまうため、担当者変更のログを残すことが難しい
    - ログ出力する形式にしなければ、後に履歴を確認するとき過去担当者が参照できない

# 課題2-4
## ORMの調査

以下の2つのORMについて調査を行う

### Prisma
- 値が必須の場合
    - OnUpdate: SetNull
    - OnDelete: Restrict
- 値が任意の場合
    - OnUpdate: Cascade
    - OnDelete: Cascade

### 理由(推測)

- 必須の場合、関連先を削除されると不整合になるため制限。更新ではNULLにして整合性を保つ。
- 任意の場合、関連先が変化しても自動追従。削除も許容。


**参考資料**
- https://www.prisma.io/docs/orm/prisma-schema/data-model/relations/referential-actions#referential-action-defaults



### TypeORM

- OnUpdate: RESTRICT
- OnDelete: Restrict


### 理由(推測)

- 自動で削除・更新しない設計思想。

**参考資料**

https://orkhan.gitbook.io/typeorm/docs/relations#relation-options

## no action、RESTRICTの違い


- MYSQL
    - RESTRICT、NO ACTIONともに被参照行の削除を防ぐ
        - チェックをトランザクション中で後回しにできない
- postgreSQL
    - RESTRICTは、被参照行の削除を防ぐ
        - チェックをトランザクション中で後回しにできない
    - NO ACTIONは、制約がチェックされた時に参照行がまだ存在していた場合に、エラーとなる
        - チェックをトランザクション中で後回しにすることができる

参考資料
https://www.postgresql.jp/docs/8.0/ddl-constraints.html
