# 他の人のレビューを行ったうえでの学び・ER 図修正

- 削除済み/支払い済み/キャンセル済み等をで持たせようとしていたが、日付で持たせるのはいいかもしれない
  - ただ、nullable のフィールドが増えるのがどうなのかは要件等
    - 以下のようなテーブルを作成することにより、拡張性が高まるとのこと。確かに高まりそうだが、そこまでやるかは諸説？
    - https://qiita.com/z_k_yama/items/6927561d4ca8b0752efe
- イミュータブルデータベースのように、menu_history のようなテーブルを作成したほうがよさそう
  - 論理削除のようなカラムを削除できるので、好ましい。
  - 過去の履歴を追いやすい＆インデックスを張りやすいのも特徴
- created_at・updated_at をリソース系のテーブルに持ったほうがよさそう
  - イベント系のテーブルについては諸説。中間テーブルに持つかも諸説。
- 商品に対するセール・合計に対するセールの双方を想定すると、price は小計と合計の双方に持つべき
- boolean のフィールドは enum 化を検討してもよさそう
  - 現状は 2 値しかないが将来的に 3 値以上に増える可能性もあるため
- order を持たせるテーブルを set_menu に移動した
  - set_menu_category はカテゴリーの定義であり、set_menu 内の順番を持たせるのは不適切と考えたため

# 修正した ER 図

```mermaid
erDiagram
order ||--|{ order_detail  : "注文詳細"
order ||--|{ order_status : "オーダーの状態"
order_status_type ||--|{ order_status: "オーダーの状態"
menu ||--o{ order_detail : "注文メニュー"
menu  ||--o| set_menu: "テーブル継承"
menu  ||--|{ menu_detail: "料金遷移"
set_menu_category　||--o{　set_menu : "所属"

order {
  bigint id PK "ID"
  varchar name "お名前"
  varchar phone_number "電話番号"
  varchar order_method "持ち帰り"
  varchar requests "その他"
  timestamp created_at "作成日"
  timestamp updated_at "更新日"
}

order_status_type {
  bigint id PK "ID"
  varchar name "ステータス名"
  timestamp created_at "作成日"
  timestamp updated_at "更新日"
}

order_status {
	bigint order_status_type_id PK "オーダーステータスID"
	bigint order_status_type_id FK "オーダーステータスID"
	bigint order_id PK "オーダーID"
	bigint order_id FK "オーダーID"
  timestamp status_datetime "変更時間"
}

menu {
  bigint id PK "ID"
  varchar menu_name "メニュー名"
  bigint set_menu_id FK "セットメニューID"
  timestamp created_at "作成日"
  timestamp updated_at "更新日"
}

menu_detail {
  bigint id PK "ID"
  bigint menu_id FK "メニューID"
  number price "値段"
  timestamp start_at "開始日"
  timestamp end_at "終了日"
}

set_menu{
	bigint id PK "ID"
	bigint category_id FK "カテゴリーID"
  bigint order "順番"
}

set_menu_category {
	bigint id PK "ID"
	varchar name "カテゴリー名"
  timestamp created_at "作成日"
  timestamp updated_at "更新日"
}

order_detail {
	bigint order_id PK "注文ID"
	bigint order_id FK "注文ID"
	bigint menu_id PK "メニューID"
	bigint menu_id FK "メニューID"
	number count "個数"
	boolean excludesWasabi "さび抜き"
}
```

# アンチパターン学習後の修正

- 特に修正事項はないと思う。
  - 顧客テーブルを持つこともできるが、あまり本質ではない気がするので、今回は未対応
- 関連するアンチパターンを列挙
  - ポリモーフィック関連
    - menu と set_menu の持ち方をどうするか。type カラムなどを持つと、メタデータがカラムに混入するので好ましくない
    - 対策としては、親テーブルを作成する(今回の対応)か、連関エンティティを作成する形式になると思われる
      - ただ、menu という親テーブルを持って、そこに対して menu と set_menu が連関エンティティを張る形式でも問題ない
      - 今回はオブジェクト指向的に、menu と set_menu が継承関係にあると判断したので、 親テーブルを採用した
  - boolean のカラムを持つこと
    - さび抜きの部分で boolean カラムを持つと将来的に性能が出ないように思われる
      - またデータ取得辞意毎回 where 句を用意する必要があるので、アプリの実装コストが重くなる
    - ただ、今回のケースだとさび抜きの寿司だけを一括で取得するクエリなどがあまり想定できないので、問題ないと思われる
    - 今回は費用の履歴の個所は、シングル世代テーブルパターンを採用したが、世代バージョンタグ付けパターンを採用することも可能
      - 最新データを見たければ view を作れば対応できるので、今回はこれで十分だと思われる
      - https://scrapbox.io/kawasima/%E3%82%A4%E3%83%9F%E3%83%A5%E3%83%BC%E3%82%BF%E3%83%96%E3%83%AB%E3%83%87%E3%83%BC%E3%82%BF%E3%83%A2%E3%83%87%E3%83%AB
