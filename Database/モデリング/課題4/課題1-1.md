# モデリング課題4

# 概要

- リマインダー
    - Slackに登録している他のユーザ（複数可）宛にリマインダーを設定できる
    - リマインダーには送信相手、文面、頻度を指定可能
    - 1時間ごとにバッチが動き、配信が必要なリマインダーを指定されたSlackユーザに配信する
- リマインダーの周期
    - 設定可能な周期は、現時点では以下の4種類（もしかすると今後増えるかもしれませんが、未定です！）
        - 毎日
        - X日おき
        - 毎週X曜日
        - 毎月X日

# 機能解釈

- リマインダー
    - Slackに登録している他のユーザ（複数可）宛にリマインダーを設定できる
        - リマインダー・ユーザーが多対多でリマインダーを設定できる
    - リマインダーには送信相手、文面、頻度を指定可能
        - リマインダーが持つプロパティが送信相手、文面、頻度の3つ
        - 【optional】人によって文面・リマインドの頻度を変えることが出来る？
            - 送信相手・文面・頻度を変えたい場合、二回リマインドを出す方が正攻法と判断
    - 1時間ごとにバッチが動き、配信が必要なリマインダーを指定されたSlackユーザに配信する
        - 1時間ごとにリマインドが送られる
            - 【仮説】つまり、時間単位でのリマインドが設定できる？
- リマインダーの周期
    - 設定可能な周期は、現時点では以下の4種類（もしかすると今後増えるかもしれませんが、未定です！）
        - 毎日
        - X日おき
        - 毎週X曜日
        - 毎月X日
    - enum型などで定義になりそう
    - バッチ自体が1時間単位での実行になる⇒実行が完了しているかの管理が必要になる
        - 毎日を指定した場合、最長でも1時間以内には実行されるようにするため
    - 実行管理(履歴管理)をする必要がある？
        - おそらく、以下の二つのどちらかが必要
            - リマインド登録時にリマインド用のテーブルにレコードを挿入する
                - 終わりがわかっていないと非現実的
                - Officeの会議予約とはこんな感じ？
            - バッチ処理が動くたびに実行履歴テーブルにレコードを挿入する
                - ただ、すでに実行したかの確認が少しめんどくさそう
                - 主キー制約を考えると、user_remainderテーブルとは別に作る必要がある
                    - 複数回実行されるため
    
    # ER図検討
    
    ```mermaid
    erDiagram
    user ||--o{ user_remainder: "リマインダー設定"
    remainder ||--|{ user_remainder: "リマインダー設定"
    user ||--o{ remainder_execution_log : "リマインダー実行ログ"
    remainder  ||--o{ remainder_execution_log : "リマインダー実行ログ"
    
        
    user {
      bigint id PK "ID"
    }
    
    remainder {
      bigint id PK "ID"
      text text "文面"
      varchar frequency "頻度"
      timestamp created_at "作成時間"
      timestamp updated_at "更新時間"
    }
    
    user_remainder {
    	bigint user_id PK "ユーザーID"
    	bigint remainder_id PK "リマインダーID"
    }
    
    remainder_execution_log {
      bigint id PK "実行ID"
      bigint remainder_id FK "リマインダーID"
      bigint user_id FK "ユーザーID"
      timestamp executed_at "実行時間"
    }
    
    ```
